# DSH Forge Prose 规范

这是编辑判断指南，不是字数竞赛。目标是让读者在没有会话记录的情况下理解当前行为、限制和风险。

## 范围和语言

执行前必须明确文件范围和 `automatic` 或 `interactive` 模式；默认使用 `automatic`。始终排除 `vendor/`。当前项目的新增文档和代码注释使用中文，稳定的 API 名称、命令、包名和代码标识保持原文。

## 完整命题

修改 prose 前先识别每个命题，并保留：

- 行动者和动作；
- 条件、时序和适用范围；
- `必须`、`可以`、`禁止` 等模态强度；
- 负向保证和例外；
- 所有权、副作用、失败行为和后果。

删除重复或过程叙述只有在这些事实仍然完整且更清楚时才成立。字数减少本身不是质量指标。

## 各类内容的覆盖要求

- 公共 API：说明返回值区别、异常、取消、时序、副作用和持久性。
- 内部注释：只说明代码无法直接表达的契约、不变量、所有权和安全边界；不要逐行解释控制流。
- 模块说明：说明职责、依赖和非显然的架构选择，并链接到决策的唯一归属文档。
- 测试说明：只保留解释夹具、真实入口、平台兼容或间接观察必要性的内容。
- README 和工程文档：说明配置、语义、失败、限制、扩展点和验证方式。
- OpenSpec：保留动机、决策、替代方案、后果、验证证据和覆盖缺口；删除计划执行过程和评审对话。

## 推理过程残留

如果读者必须看到会话、PR 或未提交草稿才能验证一段话，就把剩余事实改写成当前状态，或删除没有事实内容的段落。重点清理：审查对话、阶段编号、旧版本叙事、控制流旁白、测试 walkthrough、无标记的“以后再做”和自我辩护。

允许保留能在仓库中解析的 Issue/Note 引用、运行时旧新状态、测量边界、抑制规则理由和明确的反事实安全保证。

## 完成检查

审阅后重新读取文档，不依赖原编辑上下文；检查命令、链接、代码围栏、表格和列表结构；运行 `git diff --check`，并报告确实运行过的其他检查。
