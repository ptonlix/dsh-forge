# DSH Forge 文档规范

这是指导，不是自动脚本。执行写入前必须有明确的文档范围；不要把本技能当作授权去改动未被请求的文件。

## 真实来源

- `docs/design/`：产品和发行版设计的权威来源。
- `docs/engineering/`：工程流程、迁移边界和维护说明。
- `.agents/skills/`：智能体工作流约束，不是产品运行时文档。
- `openspec/`：提案、设计决策、任务拆分和验收状态的权威来源。

如果未来引入生成目录、站点或 schema，必须修改生成源，不要手工编辑产物；同时在对应 OpenSpec 变更中记录生成器和门禁归属。

## 放置和层级

1. 先判断读者要完成一件有顺序的工作，还是查阅一个明确范围内的事实；前者写教程，后者写参考。
2. 顶层设计文档只描述直接子系统的职责、边界和关键行为；算法、接口字段和操作步骤放到所属文档，并用相对链接连接。
3. 每个文档应能从标题和开头判断主题、适用范围、前置条件和直接子文档。
4. 重命名或移动文档是原子变更：先搜索入站链接，再移动文件并同步修复所有引用。
5. 不复制生成目录、状态清单或其他文档的整段内容；保留一个权威来源，其他位置链接过去。

## 审查重点

- 文档是否与当前配置、路径、默认值和公开行为一致。
- 代码块、命令和相对链接是否可执行、可解析、可找到目标。
- 是否把历史过程、评审对话、临时计划或重复解释误写成当前事实。
- 中文单语约定是否保持一致；英文对侧出现前，不创建半成品翻译流程。

## 验证

当前仓库的基础检查是：

```sh
git diff --check
rg --hidden --glob '!vendor/**' --glob '!.git/**' '旧路径或旧名称' .
```

当项目建立 Markdown 链接检查、格式检查或构建脚本后，将它们加入本技能和提交前技能；没有运行的检查不得报告为通过。
