# DSH Forge 代码审查

这是审查指导，不是完整清单。审查报告以问题和证据开头，按严重程度排序；没有可复现影响的纯风格偏好不应阻塞变更。

## 审查顺序

1. 确认工作树、变更范围和用户请求；不要假设未提供的 PR 基线或分支状态。
2. 阅读 diff 以及足够的上下文，确认调用方、加载路径、配置来源、资源释放和错误传播。
3. 先审正确性和数据完整性，再审生命周期、权限边界、供应链和可维护性。
4. 检查设计文档、OpenSpec 变更、README 和配置是否与实现同步。
5. 只在实际覆盖范围内要求测试；未运行的命令必须明确标记为未验证。

## DSH Forge 特有关注点

- profile、bundle、插件和桌面外壳之间的依赖方向是否保持单向。
- 第三方插件来源、固定版本、构建脚本、权限和许可证是否可追溯。
- 更新、回滚、失败启动和用户自定义 profile 是否有明确所有权。
- IPC、子进程、文件系统和网络边界是否校验输入、释放资源并隔离权限。
- 文档是否把“可配置”误写成“安全隔离”，或把示例能力误写成默认能力。

## 报告格式

每条发现包含：位置、问题、影响、复现或代码证据、建议修复方向。阻塞问题优先；跨文件的架构问题放在变更级别说明。没有发现时，明确说明仍未覆盖的测试或环境风险。
